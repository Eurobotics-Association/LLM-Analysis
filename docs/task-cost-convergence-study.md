# Convergence study: open-weight and proprietary task costs

**Research update, 31 October 2026.** Follow-up to [issue #16](https://github.com/Eurobotics-Association/LLM-Analysis/issues/16), [#9](https://github.com/Eurobotics-Association/LLM-Analysis/issues/9), [#12](https://github.com/Eurobotics-Association/LLM-Analysis/issues/12), and [draft PR #17](https://github.com/Eurobotics-Association/LLM-Analysis/pull/17). Review only: no new chart, paid run, or change to the current token-price diagram.

## Recommendation

Use **one common task outcome and one cost definition for both open-weight and proprietary models**, with the exact system and provider stated for each point. Keep AA Intelligence Index as a separate general-capability reference, and use a common coding benchmark as the proposed second diagram's vertical axis. A model may appear in both panels, but do not convert one benchmark's score into the other's or pair an AA score with unrelated task usage and label it the cost of the AA task. Connect only observed effort settings for the same model, harness, task set, and comparable provider configuration. Coverage will initially be incomplete.

The practical path is a focused public-record audit of VulcanBench's 23-task comparisons and COSPA, followed, only when a compatible complete ledger is found, by an **experimental coding-agent score versus OpenRouter cost per attempted task**. It should start with whatever matched GPT, DeepSeek and GLM configurations actually pass the evidence gates rather than promising every model or effort. The general-work panel remains a later research track. A chart that places some models at AA-derived cost and others at a different benchmark's cost would look unified but would measure different workloads, so cannot be a fair cost ranking.

## Is AA unfair to open weights?

No evidence inspected establishes that AA intentionally or systematically disadvantages open-weight models. Nor does the evidence establish that its scores or costs are equally accurate for every proprietary model. Investigate testable factors before attributing cause:

1. **Different task behavior.** AA's [Luna high vs GLM-5.3 Flash comparison](https://artificialanalysis.ai/models/comparisons/gpt-6-luna-high-vs-glm-5-3-flash) shows weighted output per task of 33k versus 134k and reasoning output of 22k versus 103k in the page captured by search. Its displayed task costs were $0.07 and $0.58, respectively. This is a plausible contributor to cost, not a decomposition of the gap; task coverage, rate choices, cache and weighting also matter. The visible AA figures are **AA estimates, not OpenRouter prices**. The scores shown by source pages can change with index version and data refresh; do not combine figures from different snapshots.
2. **Tariff selection.** The project's [30 October audit](https://github.com/Eurobotics-Association/LLM-Analysis/blob/main/docs/methodology.md) found materially different OpenRouter provider rates for GLM and DeepSeek compared with the routes used in the withdrawn chart. This is strong evidence that provider choice matters, not proof the cheapest route is workload-compatible or has equivalent quality. Recheck all endpoints, discount status and tiers on the date of any new calculation.
3. **Caching is model/provider/workload dependent.** [AA methodology](https://artificialanalysis.ai/methodology/intelligence-benchmarking) says it uses provider token counts when available and combines them with live measurements of typical cache hit rates instead of relying on the one-off evaluation cache hit. Hence AA's published cost is a modeled estimate of typical cache use, and the cost calculation has assumptions for all models. That is not by itself evidence of a skew favoring one group. The [AA API reference](https://artificialanalysis.ai/data-api/docs/reference) places token counts in Pro and provider breakdown in Commercial; neither the free figures nor Pro access alone have been shown to supply every request-level tier/cache field required by our method.
4. **Configuration can affect measured capability and spend.** A benchmark can use a different provider, precision, system prompt, effort mapping, output cap, tool parser, fallback behavior or cache policy from the OpenRouter route. Open weights permit multiple quantizations and deployments; an FP4 price cannot automatically be attached to an FP8 or undisclosed evaluation without a qualified equivalence. Proprietary endpoints also change and must satisfy the same checks.
5. **Benchmark mix and scoring.** Index weights, model judges, task types, limits, and exposed/hidden tests can favor different skills or scaffolds. A difference on one composite does not prove bias; compare matched component tasks, outcomes, prompts, provider, and repetitions before making a claim.

The [AA DeepSeek V4.1 Flash 1017 vs Luna Max](https://artificialanalysis.ai/models/comparisons/deepseek-v4-1-flash-1017-vs-gpt-6-luna) page surfaced a higher AA intelligence score for DeepSeek than Luna despite higher displayed cost. This is consistent with capability and price being separate factors; it does not establish the cost is correct or that the scores are immune to setup effects. Web source snapshots can be inconsistent or stale: record the exact version, retrieved values and date before using numbers.

## A concrete public-record audit

### COSPA: evidence for both families, incomplete cost fields

The [official336 report](https://github.com/shisa-ai/cospa/blob/main/reports/cost-performance-official336.md) compares the same 336 tasks using a common agent setup. The [aggregate points JSON](https://github.com/shisa-ai/cospa/blob/main/reports/cost-performance/points.json), Git blob `da888bea6dfdd09faf345309731bb631a54294e1` retrieved 31 October, contains per-campaign input/output totals, pass counts, effort, model IDs, and suite totals. It does not contain per-call cache-read, cache-write, context-tier, actual endpoint or retry accounting. The report's costs use configured rates and some locally hosted or free runs receive hypothetical prices, so are not automatically OpenRouter cost.

An actual row, `ds4-vanilla-low-matrix-c8-20260818`, identifies `local/deepseek-v4-flash-0731`, low effort, 108/336 passes, 281,114,680 input and 3,287,541 output tokens. The corresponding off row is 104/336, 151,947,624 input and 2,293,601 output. These are total campaign counts, not a per-request ledger. The report uses locally priced equivalents, so neither cost nor cache hits for an OpenRouter endpoint can be inferred. The public repository's [results directory](https://github.com/shisa-ai/cospa/tree/main/results) contained only `.gitkeep` when inspected; that does not establish that no records exist elsewhere. The comparison file contains GPT-5.6 Luna effort results and GLM-5.3 Flash FP8, but not all desired new models; one attempt per task limits inference.

### VulcanBench: an unusually useful per-task receipt, still not complete

The [DeepSeek comparison JSON](https://github.com/morganlinton/VulcanBench/blob/main/docs/results/swe-v4-deepseek-flash-2026-10/comparison.json), blob `52ee06d913247380177e3592c075a72ba44d83a0`, has 23 tasks at low, high and max for DeepSeek V4.1 Flash in DeepSeek Harness 0.2.1-rc.2. For low-effort `legacy-blendcore-binary-parity`, it reports functional 1, total input 2,015,208, cached input 1,956,352, and output 41,779; its receipt explicitly says cached input is included in total input. Thus the reported noncached input is 58,856, subject to upstream semantics. This is **per-task aggregate**, not 2,015,208 tokens in one request. It reports a stream hash but not the individual calls in that row; cache writes, request-level context tiers, billing events, and full retry/helper coverage are not established. Functional 1 is a functional component; do not silently treat the full composite score as a binary pass.

The [pricing check](https://github.com/morganlinton/VulcanBench/blob/main/docs/results/swe-v4-deepseek-flash-2026-10/pricing-check.json) explicitly uses DeepSeek first-party off-peak prices and notes a peak multiplier. Therefore neither its `billed_cost_usd` nor API-equivalent estimate is an OpenRouter price. A [separate Astra/Fable audit](https://github.com/morganlinton/VulcanBench/blob/main/docs/results/swe-v4-astra-fable51-2026-09/API-COSTS.md) makes the context-tier problem concrete: aggregated receipts cannot reveal per-call threshold crossings; it reports a scenario bound rather than asserting actual tiers. The source also reports fallback and helper model calls. These published examples show a path to a ledger, but do not establish that the GPT and DeepSeek rows have the same agent, exact task revision, rate scope, or that an eligible non-promotional OpenRouter route reproduces their cache behavior. No point is approved from this inspection.

## Bridge designs and their limits

| Design | What it answers | Decision |
|---|---|---|
| AA Index vs OpenRouter output-token tariff, same rules for all | General AA capability against a **price per token** | Already the current project diagram. Useful, but not task cost. No special rule by weight status. |
| One benchmark's pass@1 vs fully accounted OpenRouter cost/attempt, both model families | Cost and success on the same fixed tasks and harness policy | Preferred convergence target; currently gated on matched telemetry, compatible routes and valid scoring. |
| AA score vs cost from an independent benchmark | Broad AA capability against cost on a specified coding workload | Potential **two-source descriptive view**, only if the cost is independently verified and model/provider differences prominent; not cost of AA tasks and not a single benchmark's cost-performance curve. This is a cross-domain association, not calibration or a success-per-dollar metric. |
| AA-derived task cost for proprietary models and another benchmark's task cost for open weights | Different task suites with an apparently shared x-axis | Reject as a comparable task-cost diagram. Neither ownership category fixes the missing telemetry. |
| Fixed synthetic token workload for all | Price sensitivity for a stated hypothetical workload | Can be a separate explicitly hypothetical price calculator after route and tariff verification; does not measure actual model task cost or success. Never infer actual tokens/cache from the scenario. |
| Bounds for incomplete data | Sensitivity to explicitly bounded unknowns | Research-only, and only if totals, admissible ranges, all relevant fees and a compatible tariff are verified. Publish assumptions and label as scenarios, not confidence intervals or actual costs. Existing project rule still excludes the point from a verified cost chart while usage is incomplete. |

For a usable target chart: x = sum of all eligible OpenRouter-priced costs for attempted tasks, divided by number of attempts; y = binary task success rate, with common tasks, attempt policy and confidence interval. Keep source score, full model and revision, effort actually transmitted, agent/harness, provider/quantization, date and cost scope visible. Use a separate panel for each benchmark and version. A companion chart or table may show cost per success = all attempt costs / passes, undefined at zero passes; do not divide by an AA score or an arbitrary partial-credit percentage.

## Concrete convergence work plan

1. **Public records first, no budget:** pin the exact VulcanBench comparison, its matching GPT-6.1 Sol/Opus source rows and task hashes; compare task identities, harness, grading, effort actually sent, attempt and retry rules. Inspect each source's raw receipts to distinguish provider totals, cache read/write, fallback/helper calls and per-request context. Ask whether the actual request ledger is public; do not assume the row's path on the author's computer is accessible. Separately locate COSPA campaign artifacts or clearly document the missing release.
2. **AA fairness check:** build a small, dated matched evidence table for GPT-6 Luna and DeepSeek/GLM with AA index version, component results, model revision, AA provider/precision if disclosed, reported token usage and cache method; compare with an independent *same-task* panel at the system level. State competing hypotheses and what evidence could falsify them. Do not use vendor class as a proxy for bias or price.
3. **OpenRouter audit only for matched candidates:** collect endpoint prices and promotion status, provider/variant, quantization, route constraints, uncached/read/write/output and tier conditions; inspect all eligible routes. Reprice each call using compatible, verified category semantics and actual usage; reasoned output included in output only once. The [routing documentation](https://openrouter.ai/docs/guides/routing/provider-selection) explains provider pinning and fallback, and [cache documentation](https://openrouter.ai/blog/tutorials/prompt-caching-sticky-routing/) documents usage fields. Missing fields stay unknown. Different actual routing may change score, token counts and cache, making alternate-route prices conditional.
4. **Feasibility gate:** at least two model families and a fixed shared task panel must have complete joinable outcomes and all billable calls, tariff/availability evidence and comparable evaluation setup. Publish a traceable experimental table, with exclusions, before proposing a chart. If one category lacks evidence, show the gap, not a fabricated matching point.
5. **If a ledger is unavailable:** the least costly advance is obtaining a voluntarily shared existing ledger or collaborator-run public benchmark through OpenRouter. A new tiny pilot with a pre-agreed spend ceiling is a separate option and cannot establish a full ranking. No API spending or outreach was performed in this research.
