# Complementary task-based capability and cost: research proposal

**Review draft — 31 October 2026.** Tracking [#16](https://github.com/Eurobotics-Association/LLM-Analysis/issues/16); related [#9](https://github.com/Eurobotics-Association/LLM-Analysis/issues/9), [#10](https://github.com/Eurobotics-Association/LLM-Analysis/issues/10), [#12](https://github.com/Eurobotics-Association/LLM-Analysis/issues/12). This is a proposed second analysis, not a change to the existing [token-price methodology](token-price-methodology.md), chart, or withdrawn historical task-cost method. No diagram, new evaluation, price claim, or paid call is being published.

## Decision

A useful **capability-only research inventory** is possible now. A broad, current, defensible task-cost comparison using only existing public evidence and eligible non-promotional OpenRouter prices is **not yet established**. The leading candidates publish meaningful results, but no candidate below has yet passed an end-to-end audit of matched outcomes, complete per-call billing categories, actual provider and variant, applicable tier, retries, and an eligible OpenRouter rate for each compared configuration. This is a finding about evidence inspected, not proof that the records do not exist.

The smallest concrete missing ingredient is a **public, joinable per-call billing and configuration ledger for the exact scored attempts**: task/attempt IDs, every billable call including retries, category counts and billing semantics, context tier, actual provider/model/quantization and settings. It must be accompanied by a timestamped, complete eligible OpenRouter endpoint rate audit and an outcome ledger. An actual OpenRouter run with reconciled generation records is strongest; a counterfactual tariff applied to another provider's usage has additional transport and cache assumptions. One suitable matched pair of model/effort configurations on one fixed task panel would be enough for a first *limited* demonstration, not a broad ranking.

### Concrete observations, not cost comparisons

COSPA reports GPT-5.6 Luna 119/336 low and 140/336 max; GLM-5.3 Flash FP8 127/336 low and 116/336 xhigh; DeepSeek V4 Flash 0731 108/336 low and 100/336 xhigh. These are one-attempt, fixed-panel results from the [official report](https://github.com/shisa-ai/cospa/blob/main/reports/cost-performance-official336.md), not proof that effort causes the observed differences. Its reported dollar amounts are not adopted here. FP8 and AWQ are distinct serving configurations.

For a separate historical example, [Vals](https://www.vals.ai/benchmarks/terminal-bench-2-1) reports 87.64% for Claude Opus 5.5 and 62.92% for GLM 5.3 Flash, both labelled Terminus 2, on archived Terminal-Bench 2.1. These are system scores; the precise effort, comparable public call records, and OpenRouter repricing are unverified. They are not comparable to COSPA scores.

## Proposed protocol

### Unit and comparability

Freeze one benchmark release and task IDs, revision, task weights, grader, reference data, environment and tool permissions. State the target population and report suite-level results; do not average different benchmark versions or treat coding as general intelligence. Compare a **system**: model revision, provider and quantization, agent/harness and version, prompt, tools, context limits, effort parameter actually sent, time/turn/token limits, sampling and retry policy. Record model weight status with a source; hosted open-weight inference is not self-hosting. Effort names are vendor-specific controls, not equal units of computation; connect only observed settings of the same otherwise comparable configuration. Do not infer unobserved levels or tune a setting on the test results without disclosure.

Use the same fixed tasks and prespecified attempts for all configurations; document missing tasks and publish the common complete-case denominator alongside all attempted outcomes. Treat task timeouts, context exhaustion and model errors as failures for an operational primary metric. Report infrastructure/verifier failures separately, with a prespecified rerun policy, and count all incurred calls even where a source's score excludes them. Never remove expensive failures selectively. Any alternate benchmark-native score is separately labelled.

### Pricing each call

Store task ID, attempt ID, call/generation ID and timestamp; requested and actual model/provider/endpoint, quantization, service tier and routing/fallback; configuration and error/retry reason; request-level context/tier; billed input, cache read, cache write and write TTL, output including reasoning, other billable units and reported cost. Establish whether each count is a subset or disjoint for that provider. Preserve raw evidence with license and privacy checks. Missing fields are unknown, not zero. Include all model and helper/judge calls in the declared scope, retries and tool charges where applicable; separately state excluded infrastructure, human labor and fixed costs.

For each call and candidate eligible route, compute:

`cost = sum(disjoint billable quantity × applicable route rate) + applicable per-request/tool/other charges`

Use the applicable context and time tiers **per request**, convert rates per million appropriately, and apply cache-write TTL and billing semantics. Reasoning tokens already included in output must not be added twice. Audit all eligible, available, workload-compatible non-promotional OpenRouter endpoints at an identified timestamp; retain endpoint, rates, discounts, restrictions, quantization and evidence. Compare whole-workload totals per route, never combine cheapest categories from different providers. Free, flex and special-purpose routes require verified suitability and constraints, not automatic rejection. [OpenRouter provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) and [cache usage documentation](https://openrouter.ai/blog/tutorials/prompt-caching-sticky-routing/) explain routing and recorded cache fields; their existence does not guarantee all fields for every route.

Observed OpenRouter execution and reconciled billing establish cost for that actual route and policy. A route change may alter tokenization, model behavior, quantization, cache locality or hit rate; therefore repricing another route's exact observed usage is a **conditional estimate**, not measured success or an invoice for that route. Select the cheapest defensibly compatible route only after a full audit, and disclose the assumptions; if compatibility, actual usage categories, tier or price is unverified, exclude the cost point. Do not substitute benchmark-vendor tariffs or fixed token blends.

### Metrics and uncertainty

For each fixed cohort of attempts, let N be attempted task runs, S binary passes, and C total eligible, fully accounted inference/tool cost including unsuccessful attempts and billable retries:

- **Success rate:** S/N, with task-level results and coverage. For repeated attempts give the per-task mean pass@1 and the repeat count, rather than silently giving frequently sampled tasks more weight.
- **Cost per attempt:** C/N, with median and distribution where records support it. Define whether N includes infrastructure failures and report the alternative denominator if relevant; costs of every billable retry stay in C.
- **Cost per successful task:** C/S when S > 0; undefined when S = 0. This is observed aggregate spend per pass for the declared attempt policy, including failures. It is not the mean cost of successful attempts alone, nor a guarantee of expected cost to solve every task. Unequal task weights require corresponding explicitly stated weights.
- **Success at budget B:** fraction of the original fixed task cohort solved within B per task under a prespecified stopping/retry policy, counting all calls until success or budget exhaustion. Only report when ordered attempts and their accumulated actual/verified repriced costs support that policy; do not estimate it from an average alone. State cap overshoot and the treatment of in-flight calls.
- **Partial credit:** publish mean rubric score separately with its scale, weights, and judge; do not divide dollars by a partial score and call the result cost per success.

Give paired task-level differences and task-cluster bootstrap intervals when sufficient independent tasks and repeats exist; resample tasks with their runs, not calls as independent samples. For one attempt per task, intervals reflect task sampling under stated assumptions, not run-to-run variance. Report N, repeats, coverage, timeouts and uncertainty; correlated tasks, selection, leakage, judge bias and systematic grading defects are not fixed by a confidence interval. Avoid declaring small rank differences meaningful.

### Integrity and independence

Audit test validity and false positives/negatives, contamination and public solution access, network isolation, hidden test leakage, agent reward hacking, verifier revisions, and cherry-picked submissions. [Epoch's DeepSWE review](https://epoch.ai/benchmarks/deepswe/review) is a material systematic limitation, not a measured error rate for every model; no corrected scored release has been independently verified here. Disclose benchmark sponsors and vendor-submitted results. An open harness does not imply open model outputs, trajectories, full cost logs, independent execution, or a license to redistribute them. A shared harness controls one factor but cannot isolate intrinsic model ability from model/provider interaction or tools.

## Practical update and decision gates

1. **Now, without spending:** maintain this source-linked inventory and a dated evidence matrix. Pin upstream commits, exact release and task IDs; verify availability, license, timestamps and model/effort coverage. Request or locate complete ledgers from COSPA and VulcanBench maintainers through ordinary public issue channels only if separately authorized. Do not publish a cost chart from their displayed dollars.
2. **Smallest desk audit:** choose one COSPA or VulcanBench fixed common panel with two configurations and public attempts; trace one successful and one failed task from outcome to every call, verify per-call token semantics, retries, context, route and rates, then expand to the full declared cohort. Record missing fields and reproduce totals. Compare an actual OpenRouter endpoint against a dated all-eligible route snapshot; a single output tariff does not establish the cheapest cost.
3. **Only after evidence passes:** publish a review-only table with source fingerprints, scope, provenance, exclusions, task-level denominators and both costs and success. Require independent inspection and pricing refresh before any proposed chart. Keep capability-only information explicitly separate from any cost claims.
4. **If no public ledger exists:** seek a voluntary contributed fully instrumented OpenRouter run or design a small, fixed, reproducible pilot with a pre-agreed explicit spend ceiling, hard account controls, retries included, and isolated execution. This is a new evaluation, not the original leaderboard; no spend is assumed here. If neither is available, maintain a capability-only comparison and the existing token-price map with their limitations.

Recheck mutable source documents and endpoint prices for every update; retain archived fingerprints where licensing allows, date exclusions, and open issues for corrections. Public [issues](https://github.com/Eurobotics-Association/LLM-Analysis/issues) welcome corrections and improvement requests.
